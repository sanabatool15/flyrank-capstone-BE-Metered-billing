# Alembic Migrations Design

`src/db/migrations/` currently holds only a `.gitkeep`; the app boots via
`Base.metadata.create_all()` in `src/app.py`'s lifespan (skipped under
pytest — see that file's comment). `alembic>=1.19.1` is already a pinned
dependency in `pyproject.toml` but unconfigured. This doc specifies the
Alembic setup so it can be added without further research, while keeping
`create_all()` as a dev/test convenience fallback (not removing it — see
"Relationship to `create_all()`" below).

## File layout

```
alembic.ini                          # repo root, alongside pyproject.toml
src/db/migrations/
├── env.py
├── script.py.mako
└── versions/
    └── 0001_initial_schema.py
```

Note: `alembic.ini` conventionally lives at repo root even though the
migration scripts themselves live under `src/db/migrations/` — this matches
Alembic's default project layout and keeps `src/db/migrations/` (already
referenced by the existing `.gitkeep`) as the `script_location`.

## `alembic.ini` (repo root)

Key settings, generated by `alembic init src/db/migrations` and then edited:

```ini
[alembic]
script_location = src/db/migrations
prepend_sys_path = .
# DO NOT hardcode sqlalchemy.url here — env.py reads DATABASE_URL from
# src.config.get_settings() at runtime instead (see env.py below), so the
# same alembic.ini works against local Postgres, Supabase, or CI.
sqlalchemy.url =

[loggers]
keys = root,sqlalchemy,alembic

[logger_alembic]
level = INFO
handlers =
qualname = alembic
```

(Standard `[handlers]`/`[formatters]` sections from `alembic init`'s
default template are unchanged — omitted here for brevity.)

## `src/db/migrations/env.py`

Must import the app's actual settings and metadata rather than duplicating
connection logic:

```python
"""Alembic environment: wires migrations to src/config.py's Settings and
src/models/db_models.py's metadata, so `alembic revision --autogenerate`
diffs against the real ORM models — never hand-maintain a separate schema
description.
"""
from logging.config import fileConfig

from alembic import context
from sqlalchemy import engine_from_config, pool

from src.config import get_settings
from src.db.session import Base
import src.models  # noqa: F401 — registers every table on Base.metadata

config = context.config
if config.config_file_name is not None:
    fileConfig(config.config_file_name)

# Override alembic.ini's empty sqlalchemy.url with the real DATABASE_URL —
# same source of truth the app itself uses (src/config.py), so migrations
# always target whatever DATABASE_URL points at (local, Supabase, CI).
config.set_main_option("sqlalchemy.url", get_settings().DATABASE_URL)

target_metadata = Base.metadata


def run_migrations_offline() -> None:
    url = config.get_main_option("sqlalchemy.url")
    context.configure(
        url=url,
        target_metadata=target_metadata,
        literal_binds=True,
        dialect_opts={"paramstyle": "named"},
    )
    with context.begin_transaction():
        context.run_migrations()


def run_migrations_online() -> None:
    connectable = engine_from_config(
        config.get_section(config.config_ini_section, {}),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    with connectable.connect() as connection:
        context.configure(connection=connection, target_metadata=target_metadata)
        with context.begin_transaction():
            context.run_migrations()


if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online()
```

Important: `src/models/__init__.py` must import every model module (so
`Base.metadata` is fully populated before `env.py` reads
`target_metadata`) — verify it currently does (`from src.models.db_models
import *` or explicit imports); if it doesn't already, that's a one-line
fix bundled with this change.

## Initial migration: `0001_initial_schema.py`

Generate via:
```
uv run alembic revision --autogenerate -m "initial schema"
```
against an **empty** database (so the diff is "nothing → full schema", not
a partial diff against a `create_all()`-populated dev DB). Recommended
flow for the implementing engineer:
```
# point DATABASE_URL at a throwaway empty Postgres (local docker or a
# scratch Supabase branch/project) before running autogenerate
uv run alembic revision --autogenerate -m "initial schema"
# inspect the generated file, then apply + verify:
uv run alembic upgrade head
```

The generated migration must capture, at minimum, every table currently in
`src/models/db_models.py`:

- `tenants` (id, name, plan enum, stripe_customer_id unique, created_at)
- `subscriptions` (id, tenant_id FK, stripe_subscription_id unique, status
  enum, plan enum, current_period_end, updated_at; index `ix_sub_tenant`)
- `usage_events` (id, tenant_id FK, idempotency_key, usage_type enum,
  quantity, input/cached_input/output/reasoning tokens, cost_cents
  BigInteger, created_at; **`UniqueConstraint(tenant_id,
  idempotency_key)`** — this is the idempotency guarantee per
  `DESIGN.md`, must not be dropped or weakened; index
  `ix_usage_tenant_created`)
- `stripe_events` (id string PK = Stripe's `evt_...`, event_type,
  processed_at) — webhook dedup table
- `users` (id, email unique, auth_provider_id unique, created_at,
  last_login_at)
- `memberships` (id, user_id FK, tenant_id FK, role_id FK, created_at;
  `UniqueConstraint(user_id, tenant_id)`; indexes on tenant_id and user_id)
- `roles` (id, tenant_id FK nullable, name; `UniqueConstraint(tenant_id,
  name)`)
- `permissions` (id, name unique)
- `role_permissions` (role_id FK + permission_id FK, composite PK)
- `audit_logs` (id, tenant_id FK, actor_user_id FK nullable, action,
  resource_type, resource_id, decision, reason, created_at; index
  `ix_audit_tenant_created`)

Plus the three Postgres ENUM types (`plan_type`, `usage_type`,
`sub_status`) — `autogenerate` handles `ENUM(...)` columns correctly for
Postgres, but double-check the generated `upgrade()` creates the enum types
explicitly (via `sa.Enum(..., name=...).create(bind, checkfirst=True)` or
implicitly through `op.create_table`) since Alembic autogenerate's handling
of Postgres native enums is known to sometimes need a manual nudge —
inspect the generated file rather than assuming it's complete.

## Relationship to `create_all()`

Do **not** remove `Base.metadata.create_all(bind=engine)` from
`src/app.py`'s lifespan in this change. Rationale:
- It's explicitly skipped under pytest already (tests use their own
  in-memory SQLite engine per `tests/conftest.py`), so it doesn't conflict
  with migrations in the test suite.
- For a fresh Supabase project a stranger spins up per the README, running
  `alembic upgrade head` is the documented/correct path, but `create_all()`
  remains a harmless no-op fallback if they forget that step (it only
  creates *missing* tables, never alters/drops existing ones — see the
  existing comment in `src/app.py`).
- Removing it is a separate, deliberate decision (would make forgetting the
  migration step a hard failure instead of a soft one) — out of scope here;
  flag it as a follow-up in the PR description instead of doing it
  silently.

## Commands to document in the README (see README.md, "Migrations" section)

```bash
# apply all migrations
uv run alembic upgrade head

# create a new migration after changing src/models/db_models.py
uv run alembic revision --autogenerate -m "describe the change"

# roll back one migration
uv run alembic downgrade -1
```

## Future migrations workflow

Every future schema change: edit `src/models/db_models.py`, then run
`alembic revision --autogenerate -m "..."`, inspect the generated file,
commit it alongside the model change in the same PR — never hand-edit
`db_models.py` and skip generating a migration, and never hand-write a
migration without a corresponding model change (keeps ORM and DB schema
from drifting apart, which `MIGRATIONS_DESIGN.md`'s whole reason for
existing is to prevent).
